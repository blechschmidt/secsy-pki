Mint a TLS delegated credential (RFC 9345)

A short-lived credential a TLS terminator presents alongside the leaf certificate, so a fleet member can serve the certificate's identity without ever holding its private key — secsy-ca delegated-credential mint. It is signed by the leaf's private key, which this CA keeps for no ordinary issuance: the leaf must have been exported as a PKCS#12 with its subject key escrowed (M-of-N), and the envelope plus a quorum of recovery-agent ids must be presented here. The key is recovered only long enough to sign and is zeroized immediately. The leaf must also be delegation-eligible (a delegation_usage profile). It is minted under the CA selected above.

Adopt an existing CA

This form carries a PRIVATE KEY unless the key is already on the provider. Bring a certificate authority that exists elsewhere under this PKI — the counterpart of secsy-ca ca import. The material is sent once over this session, written into the key provider, and never echoed back to this page. An import cannot undo the key's origin: attestation will report it as imported rather than generated, so destroy every remaining copy of the key file once the CA has been exercised. Adoption passes the same four-eyes gate as creating a root.

Import a key into the provider

This form carries a PRIVATE KEY. Place an existing key on the key provider under a label without creating a CA — secsy-ca import-key — for a TSA or code-signing key that must keep its identity across a migration. The key is never echoed back, and a signing key is proved usable by a signature before the import reports success.

Provision a code-signing credential

Generate a code-signing key on the signing-role backend and issue its certificate under an existing CA, through the ordinary lint-gated issuance path — secsy-ca signing-key. A key already stored under the label is reused, so reissuing a certificate does not rotate the key. The private key never leaves the provider; what comes back is the certificate and the configuration that must reference it.

Provision the RFC 3161 TSA credential

Generate the timestamp authority's signing key on the tsa-role backend and issue it a dedicated TSA certificate — secsy-ca tsa-key. The certificate carries id-kp-timeStamping as its sole, critical extended key usage, which no issuance profile emits, so it is minted directly rather than through a profile. RSA only: openssl ts -verify interop and the CMS signer both require it.

ACME service

Automated certificate issuance (RFC 8555) for standard clients (certbot, lego, acme.sh, cert-manager). Accounts self-register with a key pair and prove control of each identifier with a challenge; every leaf is signed on the HSM through the shared CA. Read-only.

ACME does not appear to be enabled on this server. Enable it under acme: in the server config.

Certificate chain validation

Build and validate a supplied leaf (and optional intermediates) against a CA's configured trust anchors. Reports whether a chain was built, the validity window, live per-certificate revocation status (CRL + OCSP, including reversible on-hold), name-constraint and certificate-policy conformance, and weak key/signature flags — the counterpart of secsy-ca validate-cert and POST /api/validate. Hardware security module

The device this PKI's private keys live inside. Prove the hardware is genuine Yubico silicon and learn its serial, attest that a key was born on the device and cannot leave it, and read the device's own tamper-evident operation log — the counterparts of secsy-ca hsm-attest and secsy-ca hsm-audit. Device authenticity

Reads the device attestation certificate, verifies it against Yubico's published attestation CA, and makes the device answer a nonce by attesting a throwaway key labelled with it. Chain verification alone authenticates a certificate — anyone can replay a copy; only the device holding the attestation private key can answer a fresh challenge. The verified serial is the answer.

Key attestation

Ask the device to attest one asymmetric key: that it was generated inside the HSM and holds no capability permitting export. Attesting by CA additionally binds the result to that CA's certificate, so the verdict describes the key the CA actually signs with rather than merely some object on the device.

Device-wide attestation audit

Attest every asymmetric key the provider holds in one pass and report which ones fail policy — the counterpart of secsy-ca hsm-attest audit. It answers a question no single-key check can: not "is this key safe" but "is anything on this device exportable". A key created exportable-under-wrap, or imported rather than generated, stays invisible until something enumerates them. Each key is judged on the device's own assertions, with no expected key imposed, and a key that cannot be attested is a row carrying its error rather than a failed pass.

Import an existing signing key

Adopt a key you already have — one whose public half is embedded in shipped clients cannot be rotated cheaply, but it can be moved off an application server and into the HSM. This form carries a private key. It is sent once over this authenticated session, written into the provider non-extractable, never echoed back and never logged; the field is cleared as soon as the import succeeds. An imported key is not equivalent to a generated one: hardware attestation will report it as imported, and any copy made before the import remains a copy — destroy the remaining copies once the key has been exercised. Requires secret:signing-key, like creation. The counterpart of secsy-secret signing-key import.

An RSA key must name its algorithm: the same key works with PSS and with PKCS#1 v1.5, and the choice has to match what the existing verifiers already do. An EC or Ed25519 key determines its own.

Tokenization — format-preserving encryption (FF1, NIST SP 800-38G) through a named template

Encode a value into a token of the same shape (a card number stays a card number), then decode it back. The per-template key is derived from a KEK-sealed seed, so a deterministic template makes tokens searchable while the plaintext never leaves the envelope. Templates are defined in secret.transforms; you need secret:transform plus any per-template role allowlist.

KEK rotation — generate the next key-encryption key, re-wrap onto it, retire the old one

Rotation generates a fresh KEK inside the HSM and makes it active. Existing envelopes keep decrypting under the retiring version, so nothing breaks; re-wrapping moves stored data keys onto the active version, and only once none remain can the old version be retired. Data ciphertext and escrow shares are never touched. Requires secret:rotate; rotate and retire additionally demand a passkey step-up.
